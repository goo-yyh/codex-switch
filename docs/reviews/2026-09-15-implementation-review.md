## 按优先级排列的问题

### R1 · P1：修改服务地址后，会把旧 Key 发送给新服务

**位置：** `apps/desktop/src-tauri/src/main.rs:84`、`:98`、`:107`；`apps/desktop/src/App.tsx:70`、`:413`。

**触发：** 编辑已有连接，切换服务商或修改为另一主机的地址；按界面“留空保留原密钥”的提示，不填写新 Key。

**实际行为：** 后端先按旧连接 ID 从 Vault 读取 Key，再调用新地址进行验证。直到验证结束，才读取旧连接、比较地址并决定是否创建新 ID。这样旧服务的密钥已经进入新服务的认证请求，即使验证最终失败也无法撤回。

**证据等级：** 确定的源码调用顺序；没有使用真实密钥进行外发复现。

**建议：** 在读取旧 Key 和发请求前加载旧连接，验证凭据适用范围。跨服务商或跨 origin 必须填写新 Key；同主机不同套餐路径也应有明确的复用规则。前端同步清除“已保存密钥”的提示。新建路由 ID 不能代替凭据范围校验。

**回归要求：** Mock Vault 和 HTTP transport；跨域修改且 Key 留空时应在发送 HTTP 前失败。相同凭据范围内只改模型时可以复用；显式填写新 Key 时只能发送新 Key。

### R2 · P2：流式工具结果回传会丢失已缓存的推理上下文

**位置：** `crates/core/src/protocol.rs:421`、`crates/core/src/gateway.rs:99`。

**触发：** Chat 上游返回 `reasoning_content` 和工具调用；客户端收集 `response.output_item.done` 的工具项，执行工具后通过完整 `input` 回传，不携带 `previous_response_id`。

**实际行为：** `output_item.done` 发出后才给最终响应中的工具项补 `reasoning_content`，因此事件项不包含它。网关虽然缓存了最终响应，但 `enrich()` 仅在存在 `previous_response_id` 时工作，不能按调用 ID 补回已有工具项的元数据。下一轮 Chat 请求的 assistant 工具消息因此缺少原来的推理内容。

**证据等级：** 隔离 Rust 测试已复现数据丢失，实际值 `null`，预期为合成推理文本。没有据此声称所有模型都会报错，也没有验证真实 App 一定采用此路径；需要推理上下文的模型存在工具续接失败风险。

**CC Switch 参考：** [codex_chat_history.rs](https://github.com/farion1231/cc-switch/blob/06082e189d65e6d6dbadc35dacdac1ce6c79d89a/src-tauri/src/proxy/providers/codex_chat_history.rs#L89) 同时处理已有调用项和调用结果，在缺少 previous ID 时通过唯一 call ID 查找，并为已有调用项补回缓存字段。

**建议：** 保存真实的工具调用元数据，支持按 response ID 和唯一 call ID 补全；保持连接隔离、冲突检测和缓存上限。不要依赖客户端保留非标准字段，也不要用虚构的 reasoning 文本填空。测试要覆盖事件项回放、完整历史、增量历史、同名 call ID 冲突和缓存失效。

### R3 · P2：较长的命名空间工具名会拒绝整次请求

**位置：** `crates/core/src/protocol.rs:30`。

**触发：** 工具命名空间与工具名各 40 个 ASCII 字符；每段都不长，但拼接后的 `namespace__name` 达到 82 字符。

**实际行为：** 转换器直接报“工具名称重复或过长”。即使本轮不会调用这个工具，只要工具定义存在，请求就无法发送。这会限制 MCP 等带前缀的工具集合。

**证据等级：** 隔离 Rust 测试已复现。

**CC Switch 参考：** [flatten_namespace_tool_name](https://github.com/farion1231/cc-switch/blob/06082e189d65e6d6dbadc35dacdac1ce6c79d89a/src-tauri/src/proxy/providers/transform_codex_chat.rs#L1314) 使用限长前缀和短哈希编码。

**建议：** 建立稳定、限长、可反查的工具名映射，定义、历史调用和指定 `tool_choice` 必须共用同一映射。验证两个共同长前缀的工具不会碰撞，映射后的响应能还原 namespace/name。

### R4 · P2：显式禁止并行工具调用的参数被静默丢弃

**位置：** `crates/core/src/protocol.rs:146`；模型目录声明见 `crates/core/src/providers.rs:106`。

**触发：** 请求带有工具定义和 `parallel_tool_calls: false`。

**实际行为：** 转换后的 Chat 请求缺少该字段，行为由上游默认值决定，与本地模型目录的 `supports_parallel_tool_calls: false` 不一致。输入中的 `temperature`、`top_p` 也没有转换，但本次失败断言专门针对工具并行策略。

**证据等级：** 隔离 Rust 测试已复现，实际为字段缺失，预期为布尔值 false。未声称某一家模型在此次审查中实际并行调用了工具。

**CC Switch 参考：** [转换参数及无工具时清理](https://github.com/farion1231/cc-switch/blob/06082e189d65e6d6dbadc35dacdac1ce6c79d89a/src-tauri/src/proxy/providers/transform_codex_chat.rs#L324) 保留该参数，并避免在没有工具时发送它。

**建议：** 定义明确的参数转换白名单，保留显式 false；不能支持的语义应明确处理。测试有工具、无工具、字段缺失和显式 false 的区别。

### R5 · P2：验证中返回首页，后台流程仍会继续开启和打开应用

**位置：** `apps/desktop/src/App.tsx:113`、`:139`、`:350`。

**触发：** 点击“配置并打开 Codex”，验证尚未完成时点击“返回”。

**实际行为：** 页面返回首页，取消验证按钮消失；但等待中的 `save()` 没有取消或失效检查，验证成功后仍会执行 `set_enabled` 和 `open_codex`。首页、设置等导航也没有阻止离开操作页。

**证据等级：** React 测试使用完全模拟的原生桥，已复现离开页面后仍调用开启/打开命令；未运行真实 App。

**建议：** 最简单的修复是操作期间禁用离开页面的入口，保留明确的取消按钮。若允许离开，则取消验证并使本次工作流失效，在每一步副作用前检查请求身份。原生命令各自的 mutex 不能替代整个多步工作流的取消语义。

### R6 · P2：开启流程跨资源写入缺少失败补偿

**位置：** `apps/desktop/src-tauri/src/main.rs:164` 至 `:215`。

**触发：** 网关已启动后模型目录写入或配置切换失败；或者配置已应用，最后写入 SQLite 的 selected 失败。

**实际行为：** 网关先保存到 runtime，随后更新 routes、写目录、改配置，最后保存 selected。后续步骤通过 `?` 返回时没有统一补偿。配置冲突时可能留存已启动的网关和目录文件；最后一步数据库失败时则可能出现配置已指向新模型、界面仍选择旧模型，而且 pending reload 尚未更新。`snapshot()` 有条件清理网关，但不是整个操作的事务恢复。

**证据等级：** 源码确认的失败路径，尚未对 Tauri 协调层做可注入故障的运行复现。这里不是指 `ConfigManager` 的原始备份失效。

**CC Switch 参考：** [rollback_failed_takeover_activation / rollback_hot_switch_preparation](https://github.com/farion1231/cc-switch/blob/06082e189d65e6d6dbadc35dacdac1ce6c79d89a/src-tauri/src/services/proxy.rs#L819) 为接管和热切换失败提供显式恢复路径。只参考补偿机制，不照搬其 auth 处理范围。

**建议：** 把开启/切换抽为可测试的协调层，区分准备、应用、提交。保留“开启前基线”和“此次切换前状态”两个不同概念；失败时恢复本次操作前的可用状态，关闭时仍恢复首次开启前的原配置。用模拟网关、凭据库与 App 启动器，对每个写入阶段注入失败。

### R7 · P2：一个未选中连接的 Key 不可读，会阻断所有连接开启

**位置：** `apps/desktop/src-tauri/src/main.rs:144`。

**触发：** 已保存 A、B 两个连接，用户选择 A，B 的凭据被删除或无法读取。

**实际行为：** `routes()` 遍历所有连接并用 `collect::<Result<_>>()` 汇总；任何一次 Vault 读取失败都会使 A 的开启失败。`enable_inner()` 在此之后才寻找选中的连接。用户只能收到笼统的“重新填写”提示。

**证据等级：** 源码确认；没有修改真实 Keychain。

**建议：** 区分选中连接、已有任务所需连接和不可用连接；按路由读取凭据或维护独立的可用性状态，不能因无关连接失败而阻断健康连接，也不能把旧路由悄悄转到别的凭据。Mock A 可读、B 缺失，验证 A 可开启且 B 显示明确错误。

## 产品与维护优化

这些与上述缺陷分开安排：

1. **“仅验证并保存”的动作要与文案一致。** `App.tsx:121` 仍调用 `select_connection`；开启期间这会修改默认配置。产品文档已有解释，但按钮本身无法表达副作用。建议保存只保存，使用单独的“设为默认”动作。
2. **明确异常恢复状态。** 启动时 journal 可以是 enabled，而 runtime 是 None；目前依靠用户点击重新建立路由，文档也明确说明。建议首页呈现“连接待恢复”和直接恢复入口。自动恢复路由可单独设计，不必自动启动或重启 Codex。
3. **清理失效目录文件。** 每次 enable 都创建新的 UUID catalog 文件；应按当前配置、恢复记录和仍在运行的任务引用进行回收，不能直接删除所有旧文件。
4. **保持简单 UI，改善出错路径。** 把“已保存”“正在验证”“正在连接”“等待应用重新打开”作为明确状态，减少依赖几组布尔值和错误字符串推导状态。
5. **官网发布信息集中管理。** 当前下载页正确标注安装包待发布、Windows 待验证；正式发布时统一版本、架构、下载地址和校验信息。应用内文档入口目前硬编码 GitHub Markdown 地址，可以改为可配置的独立产品文档地址，不依赖原有中文站。
6. **服务预设与兼容证据分开。** 官网“现在都能连接”容易被理解为全部完成验证。宜写成“内置五家服务预设”，把验证日期、接口、模型和套餐适用范围放在兼容页。现有供应商报告不能代表真实 App 验收，本次没有重测其结果。
7. **测试重点转到协调层和完整协议回放。** 现有 React 测试模拟整个 native bridge，核心 Rust 测试不执行 Tauri 命令。两者之间的保存、Vault、网关、配置、SQLite、启动顺序正是 R1/R6/R7 所在位置。
